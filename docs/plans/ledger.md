# Plan: ledger

Status: ships in this change. New top-level package. Phase 34 owns
the full design contract; see
docs/plans/agents/phase34_ledger.md for the exhaustive API
prose, the error-ordering rules, and the retry-and-reclassify
contract every mutating method follows. This document is the
package-level summary the plan gate requires.

## Goal

Give a caller a durable-task-admission primitive. A task submitted
under an idempotency key is admitted exactly once, even under retry
or duplicate submission. Ownership moves between processes through a
time-boxed lease with renewal and a fenced takeover. A failed task
marks its dependents blocked.

## Scope

Inside: idempotency-keyed admission (`Admit`) with a sequence
watermark; lease-based ownership (`Claim`, `Renew`, `Release`) with a
monotonic fence token; a stale-lease takeover (`Takeover`);
transitive dependency blocking on failure (`Complete`); a pluggable
`Store` with a shipped in-memory default (`MemStore`); and
`Snapshot`/`Encode`/`Decode`/`Restore` for point-in-time persistence.

Outside: a shipped durable backend beyond `MemStore`, distributed
consensus, network transport, task scheduling or prioritization, a
worker-pool type, and event-sourced history. `ledger` defines the
`Store` seam a caller crosses to reach real durability; it ships only
the in-memory implementation. See phase 34's Scope section for the
full reasoning behind each exclusion.

`ledger` reuses `machine.Status` for its five task states instead of
inventing a second enum, and it imports `events` for its typed event
names, matching the emit pattern `machine` and `flow` already carry.
It imports no other package; the row in `policy/layers.json` is
`"ledger": ["machine", "events"]`.

## API

The exported surface lives in `api/ledger.txt`, generated by
`make api-update`. The full reasoning behind every method's error
order and its retry-and-reclassify behavior on a losing
`CompareAndSwap` is in phase 34's API section; the summary below
names the surface only.

- `IdempotencyKey`, `OwnerID`, `Sequence`, `FenceToken` — the typed
  identifiers.
- `StatusPending`, `StatusClaimed`, `StatusCompleted`, `StatusFailed`,
  `StatusBlocked` — the five task states as `machine.Status` values.
- `TaskState` and `TaskState.Validate` — the per-key record and its
  field invariants.
- `Store` — the pluggable backend: `Load`, `CompareAndSwap`, `Range`.
  `CompareAndSwap` compares `(Sequence, Status, Fence, Rev)`; `Rev`
  closes the blind spot two concurrent same-fence `Renew` calls would
  otherwise leave.
- `MemStore` and `NewMemStore` — the shipped mutex-guarded `Store`.
- `Ledger` and `New` — the handle over one `Store` and an optional
  `events.Bus`.
- `Admit`, `Claim`, `Renew`, `Release`, `Takeover`, `Complete`,
  `State`, `Blocked` — the mutating and read operations.
- `Snapshot`, `Snapshot.Validate`, `Snapshot.Encode`, `Decode`,
  `Restore` — point-in-time persistence for `MemStore`.
- `AdmittedEvent`, `ClaimedEvent`, `RenewedEvent`, `ReleasedEvent`,
  `TakenOverEvent`, `CompletedEvent`, `BlockedEvent` — the typed
  `events.Name` constants, emitted after the matching
  `CompareAndSwap` succeeds.
- `ErrLeaseActive`, `ErrFenced`, `ErrNotStale`, `ErrNotClaimed`,
  `ErrNoKey`, `ErrUnknownStatus` — the sentinel errors, checked with
  `errors.Is`.

A cyclic dependency graph deserves a specific note beyond phase 34's
text: `Complete`'s blocking walk seeds a matching-target set with the
failed key and grows a separate write-target set only through a
genuine `Needs` edge. An ordinary tree-shaped `Needs` graph never
routes back to the failed key, so the failed key stays at its
terminal status (`StatusCompleted` or `StatusFailed`) set by
`Complete`'s own primary write. A real cycle (`A.Needs` contains `B`,
`B.Needs` contains `A`) routes back to the failed key through a real
edge, so the failed key joins the write-target set like any other
affected key and ends `StatusBlocked`, overwriting its own terminal
write from the same `Complete` call. This is why the phase 34 Tests
section's two-hop and three-hop cycle cases expect every node in the
cycle, including the originally failed key, to end `StatusBlocked`.

## Tests

Test files live in `ledger/ledger_test/`, matching the layout phase
34 names: `admit_test.go`, `claim_test.go`, `takeover_test.go`,
`complete_test.go`, `snapshot_test.go`, `mem_store_test.go`,
`admit_integration_test.go`, the five `*_race_test.go` files run
under `go test -race` (`claim_race_test.go`, `admit_race_test.go`,
`takeover_race_test.go`, `renew_race_test.go`,
`complete_race_test.go`), and `admit_bench_test.go`. Two additional
files round out coverage beyond phase 34's named list:
`task_state_test.go` table-drives every `TaskState.Validate` rule,
and `context_test.go` covers the retry loop's `ctx.Err()` exit, the
`Store`-level context checks, `Snapshot.Encode`'s and `Restore`'s
error paths, and `Blocked`'s `Store.Load` error propagation.
`helpers_test.go` holds the shared fixtures (`newLedger`, `mustAdmit`,
`mustClaim`, `buildCompleted`, `buildFailed`, `buildBlocked`,
`fixedNow`, `fixedLease`) every other file in the package reuses.
