# Plan: ledger

Status: shipped. New top-level package, from phase 34. Phase 42 later
adds a second `Store` implementation, `SQLiteStore`, behind the
`ledger_sqlite` build tag. See `docs/packages/ledger.md`'s
"SQLiteStore" section for the shipped surface. This document covers
the phase-34 surface `ledger` shipped with: `MemStore` and everything
above it. Depends on the
shipped `machine` and `events` packages only; `ledger` does not import
`heartbeat`. `LeaseUntil` compared against a caller-supplied `now` is
the only staleness signal `Claim` and `Takeover` read; `ledger` keeps
no separate liveness state.

`ledger` is not `flow`: `flow` runs one in-process graph of steps to
completion in one call, its state living on the Go stack for the
duration of `Run`. `ledger` records the admission and ownership of
independent tasks across process restarts and across a worker pool. A
`flow.Run` invocation can itself be the task body a `ledger` owner
claims and executes; the two compose, neither wraps the other. `ledger`
is not `machine` either: it reuses `machine.Status` and a
`machine.Definition` internally to name and validate its five task
states instead of inventing a second enum, and adds what `machine`
does not have: an idempotency key, a claim lease, a fence token, and
dependency-driven blocking. `ledger` composes with `durablefence`'s
`Scenario` harness (`docs/plans/durablefence.md`) to prove its claim,
takeover, and fence invariants without a second copy of that test
logic; `durablefence` names `ledger` as its first intended adopter.
`ledger` is also distinct from `flow`'s retry policy (shipped by
phase 30; see `docs/plans/flow.md`): `RetryPolicy` re-runs a failed
step under backoff inside one process, one graph walk, while
`ledger.Admit` makes an out-of-process retry (a whole new process
picking up the task) safe by rejecting the second attempt under the
same idempotency key instead of re-running it. A caller may layer
both: `flow` retries a step in-process, and if the process dies
mid-step, a second process calls `ledger.Takeover` and resumes
ownership.

## Goal

Give a caller a durable-task-admission primitive. A task submitted
under an idempotency key is admitted exactly once, even under retry
or duplicate submission. Ownership moves between processes through a
time-boxed lease with renewal and a fenced takeover. A failed task
marks its dependents blocked.

## Scope

Inside: idempotency-keyed admission (`Admit`) with a sequence
watermark; lease-based ownership (`Claim`, `Renew`, `Release`) with a
monotonic fence token; a stale-lease takeover (`Takeover`);
transitive dependency blocking on failure (`Complete`); a pluggable
`Store` with a shipped in-memory default (`MemStore`); and
`Snapshot`/`Encode`/`Decode`/`Restore` for point-in-time persistence.

Outside (at phase 34): a shipped durable backend beyond `MemStore`.
Phase 42 later adds `SQLiteStore`, an opt-in, `ledger_sqlite`-
build-tag-gated `Store` backed by `modernc.org/sqlite`, next to
`MemStore`; see `docs/packages/ledger.md`'s "SQLiteStore" section.
`MemStore` stays the default, zero-dependency `Store`; `New`'s
nil-`Store` fallback is unchanged by that addition. Outside:
distributed consensus — `ledger` does not elect a leader or replicate
`Store` across nodes; a caller who needs consensus runs `Store`
against a backend that already provides it, and `ledger`'s own
`CompareAndSwap` calls compose with that guarantee without knowing it
exists. Outside: network transport — moving a claim or an admission
request between processes over a wire is already `a2aclient`'s
concern for the agent-to-agent case; `ledger` is a local API each
process calls against its own `Store` handle. Outside: task
scheduling or prioritization — `ledger` records which task is
admitted, owned, and blocked, not which pending task a caller should
claim next. Outside: a generic worker-pool type — a caller composes
`ledger` into their own pool. Outside: event-sourced history —
`Snapshot` stores one row per task, the current state, not an
append-only log; a caller who needs a replayable history keeps their
own log of the events `ledger` emits on the bus.

`ledger` reuses `machine.Status` for its five task states instead of
inventing a second enum, and it imports `events` for its typed event
names, matching the emit pattern `machine` and `flow` already carry.
It imports no other package; the row in `policy/layers.json` is
`"ledger": ["machine", "events"]`.

## API

The exported surface lives in `api/ledger.txt`, generated by
`make api-update`.

- `IdempotencyKey`, `OwnerID`, `Sequence`, `FenceToken` — the typed
  identifiers. `Sequence` is the caller-assigned watermark `Admit`
  rejects a duplicate or late submission against. `FenceToken` is a
  monotonic counter `Claim` and `Takeover` return; `Renew`, `Release`,
  and `Complete` reject a stale token, so a dispossessed owner's late
  call never mutates the record.
- `StatusPending`, `StatusClaimed`, `StatusCompleted`, `StatusFailed`,
  `StatusBlocked` — the five task states as `machine.Status` values.
- `type TaskState struct { Key IdempotencyKey; Status machine.Status; Sequence Sequence; Owner OwnerID; Fence FenceToken; LeaseUntil time.Time; Needs []IdempotencyKey; BlockedBy IdempotencyKey; Task any; Rev uint64 }`
  and `TaskState.Validate` — the per-key record and its field
  invariants: an empty `Key`, an out-of-range `Status`, a `Needs`
  entry equal to `Key` (a direct self-cycle), a `BlockedBy`/`Status`
  mismatch, and a `StatusClaimed` record with an empty `Owner` or a
  zero `LeaseUntil` are all rejected. `Task` is caller-owned, like
  `machine.InOut.Input`; `ledger` never inspects it. `Rev` is a
  `Store`-assigned revision counter no `Ledger` method sets or
  interprets itself; it only forwards the loaded value into
  `CompareAndSwap`'s `old` argument.
- `Store` — the pluggable backend: `Load`, `CompareAndSwap`, `Range`.
  `CompareAndSwap` compares `(Sequence, Status, Fence, Rev)`, not
  full-struct or `Task`-field equality, since `Task` is a caller-owned
  `any` with no defined cross-implementation equality. `Rev` exists
  because `(Sequence, Status, Fence)` alone is blind to a `Renew`
  call: `Renew` only extends `LeaseUntil`, so two concurrent same-fence
  `Renew` calls would read an identical three-field tuple and both
  succeed, silently dropping the first writer's extension. A
  conforming `Store` bumps the stored `Rev` by one on every successful
  `CompareAndSwap`, regardless of which fields changed, so the second
  `Renew`'s stale `old.Rev` fails against the first `Renew`'s bump like
  any other conflicting write. `Range`'s `fn` must not call any other
  `Store` method on the same `Store`: `Range` may hold a lock for the
  duration of the iteration, and a reentrant call from inside `fn` can
  deadlock against it; `Complete`'s blocking walk follows a two-pass
  shape for this reason (collect in `Range`, mutate after it returns).

  Every mutating method (`Admit`, `Claim`, `Renew`, `Release`,
  `Takeover`, `Complete`) follows the same retry-and-reclassify
  contract on a losing `CompareAndSwap`: it re-loads the current
  record and re-evaluates its own eligibility rule against the fresh
  record, instead of surfacing a generic CAS-failure result. When the
  fresh record is no longer eligible (a different owner now holds a
  live lease, or the record already reached the target state), the
  method returns its own declared sentinel error at once. When the
  fresh record is still eligible (for example a losing `Renew` racing
  a second `Renew` from the same owner and fence, whose `CompareAndSwap`
  lost only because the first `Renew` already bumped `Rev`), the
  method retries `CompareAndSwap` against the fresh record, repeating
  reload-reclassify-retry until it succeeds, becomes ineligible, or
  `ctx` is canceled or its deadline passes, in which case it returns
  `ctx.Err()`. This means a losing `Claim` or `Takeover` always
  surfaces through its sentinel error, while a losing `Renew`,
  `Release`, or `Complete` against a record the caller still
  legitimately owns keeps retrying until its write lands, so no
  legitimate lease extension, release, or completion is silently
  dropped by a same-owner race, and no illegitimate one is silently
  accepted.
- `MemStore` and `NewMemStore` — the shipped mutex-guarded `Store`.
  Default when `New` gets a nil `Store`. `NewMemStore` is unbounded:
  every admitted record stays in memory for the life of the process.
- `MemStoreOptions` and `NewMemStoreWithOptions(opts) (*MemStore, error)`
  (phase 42b) — an opt-in bounded-entry-cap knob for `MemStore`.
  `MemStoreOptions.MaxEntries`, when positive, tombstones the oldest
  terminal record once the store's live entry count exceeds the cap,
  instead of deleting it: `Task` and `Needs` are cleared and `Owner`
  and `LeaseUntil` are zeroed, but `Status` and `Sequence` survive, so
  `Admit`'s idempotency check still rejects a re-admission at the
  tombstoned key. A `StatusPending` or `StatusClaimed` record is never
  tombstoned. A caller who needs every evicted record's original
  `Task` payload preserved must not enable `MaxEntries`.
  `NewMemStoreWithOptions` returns a wrapped `ErrInvalidMaxEntries` for
  a negative `MaxEntries`. `Ledger.Restore` into a `MaxEntries`-bounded
  `MemStore` is out of scope: its `liveCount` and eviction order may
  not reflect the pre-snapshot state.
- `Ledger` and `func New(store Store, bus *events.Bus) (*Ledger, error)`
  — the handle over one `Store` and an optional `events.Bus`; a nil
  `store` defaults to `NewMemStore()`, a nil `bus` disables events,
  matching the `flow` and `machine` emit contract.
- `Admit(ctx, key, seq, task any, needs ...IdempotencyKey) (bool, error)`
  — CAS-admits a `StatusPending` record when the key is absent or the
  stored sequence is lower and the stored status is `StatusPending` or
  `StatusClaimed`. A need already `StatusFailed` or `StatusBlocked`
  lands the new record `StatusBlocked`, naming that need in
  `BlockedBy`: a dependent arriving after its dependency's failure
  blocks at admission, matching what `Complete`'s dependent scan does
  for records that exist first. A `Store` fault reading a need fails
  the call; admission never guesses between pending and blocked. Returns `false, nil`, not an error, for a duplicate,
  late, or post-terminal submission: a retrying caller never branches
  on an error type to detect its own retry or resurrect a finished
  result.
- `Claim(ctx, key, owner, lease, now) (FenceToken, error)` — claims a
  `StatusPending` record, or a `StatusClaimed` record whose
  `LeaseUntil` is at or before `now`. Checks `ErrNoKey` first, before
  any status precondition, so a never-admitted key never falls through
  to `Store`'s insert-if-absent convention. Returns `ErrLeaseActive`
  when another owner's lease is still live.
- `Renew(ctx, key, owner, fence, lease, now) error` — extends
  `LeaseUntil`. Checks `ErrNoKey`, then `ErrNotClaimed` (status is not
  `StatusClaimed`), then `ErrFenced` (stale token).
- `Release(ctx, key, owner, fence) error` — returns a claimed record to
  `StatusPending`. Checks `ErrNoKey`, then `ErrFenced`, then
  `ErrNotClaimed`.
- `Takeover(ctx, key, owner, lease, now) (FenceToken, error)` — claims
  a `StatusClaimed` record whose lease has expired, through the same
  `Store.CompareAndSwap` call `Claim` uses, so a `Claim` and a
  `Takeover` racing the same just-expired lease resolve on one CAS,
  not two independent checks that could disagree. Bumps `FenceToken`
  past the prior value, fencing the dispossessed owner out. Checks
  `ErrNoKey`, then `ErrNotStale` (lease still live), then
  `ErrNotClaimed` (a `StatusPending` or terminal record; use `Claim`
  for a never-claimed one).
- `Complete(ctx, key, owner, fence, status machine.Status) error` —
  accepts only `StatusCompleted` or `StatusFailed`; an out-of-range
  `status`, checked before any `Store` call, returns
  `ErrUnknownStatus`. Then checks `ErrNoKey`, `ErrFenced`, and
  `ErrNotClaimed` (including a record `Complete` already moved to a
  terminal status: a second call against it never mutates it, even
  with a matching fence). On `StatusFailed`, walks the dependency
  graph and sets `StatusBlocked` with `BlockedBy` on every record that
  transitively names the failed key in `Needs`. The walk keeps a
  visited-key set, so a cycle across two or more `Admit` calls
  terminates instead of looping; the failed key itself keeps its own
  terminal status, since the terminal-status skip below protects it
  the same way it protects any other already-resolved dependent. The
  walk touches `Store` in two passes: one `Range` call collects every
  record into an in-memory list with no further `Store` call from
  inside `fn`; an in-memory step then computes transitive `Needs`
  membership from that list; a second pass calls `CompareAndSwap` once
  per affected key, skipping a key whose freshly loaded record already
  carries a terminal status (`StatusCompleted`, `StatusFailed`, or
  `StatusBlocked`), so a dependent that finished on its own, or was
  already blocked by an earlier, unrelated failure, keeps its recorded
  outcome. Pass two's per-key write retries on a losing
  `CompareAndSwap` against a still-non-terminal fresh record, closing
  the gap where a concurrent write to a dependent between the `Range`
  snapshot and pass two's visit — for example a `Claim` that bumps the
  dependent's `Rev` — would otherwise leave it silently unblocked.
- `State(ctx, key) (TaskState, bool, error)` — the current record; the
  bool is a found signal, not an error, for a missing key.
- `Blocked(ctx, key) (IdempotencyKey, bool, error)` — the blocking
  ancestor when `key` is `StatusBlocked`. The bool answers only
  "currently blocked," the same `false` for a never-admitted key and
  for an admitted, unblocked one; a caller who needs to tell those
  apart calls `State` first. `Blocked` performs no `CompareAndSwap`.
- `Snapshot`, `Snapshot.Validate`, `Snapshot.Encode`, `Decode`,
  `Restore` — point-in-time persistence for `MemStore`, mirroring
  `flow.Checkpoint`'s `Validate`/`Encode`/`Decode` shape. `Restore`
  inserts every record through `CompareAndSwap`; meant for `MemStore`
  cold-start or test setup, since a `Store` already backed by durable
  storage needs no `Restore` call.
- `AdmittedEvent`, `ClaimedEvent`, `RenewedEvent`, `ReleasedEvent`,
  `TakenOverEvent`, `CompletedEvent`, `BlockedEvent` — the typed
  `events.Name` constants, emitted after the matching
  `CompareAndSwap` succeeds, never before.
- `ErrLeaseActive`, `ErrFenced`, `ErrNotStale`, `ErrNotClaimed`,
  `ErrNoKey`, `ErrUnknownStatus`, `ErrInvalidMaxEntries` — the
  sentinel errors, checked with `errors.Is`.

A cyclic dependency graph deserves a specific note: `Complete`'s
blocking walk seeds a matching-target set with the failed key and
grows a separate write-target set only through a genuine `Needs`
edge. An ordinary tree-shaped `Needs` graph never routes back to the
failed key, so it stays at its terminal status set by `Complete`'s
own primary write. A real cycle (`A.Needs` contains `B`, `B.Needs`
contains `A`) routes back to the failed key through a real edge, so
it joins the write-target set like any other affected key; pass two's
terminal-status skip still protects it there, the same way it
protects any other already-terminal dependent, so it keeps its
terminal status instead of being overwritten to `StatusBlocked`. A
two-hop and a three-hop cycle case both pin this: the originally
failed key keeps its terminal status, while every other node in the
cycle ends `StatusBlocked` exactly once.

## Tests

Test files live in `ledger/ledger_test/`: `admit_test.go`,
`claim_test.go`, `takeover_test.go`, `complete_test.go`,
`snapshot_test.go`, `mem_store_test.go`, `admit_integration_test.go`,
the five `*_race_test.go` files run under `go test -race`
(`claim_race_test.go`, `admit_race_test.go`, `takeover_race_test.go`,
`renew_race_test.go`, `complete_race_test.go`), `admit_bench_test.go`,
`task_state_test.go`, and `context_test.go`.

- `admit_test.go` — the first `Admit` for a key succeeds; a second at
  the same or a lower sequence is a no-op; a second at a higher
  sequence rebases a `StatusPending` or `StatusClaimed` record but
  never a terminal one; `AdmittedEvent` fires once per successful
  admission only.
- `claim_test.go` — `Claim` succeeds on a pending record and fails
  with `ErrLeaseActive` while another owner's lease is live, then
  succeeds for a new owner once the lease expires; `Renew` extends
  the lease under the current fence and fails with `ErrFenced` or
  `ErrNotClaimed` otherwise; `Release` returns a record to
  `StatusPending` under the current fence; each of `Claim`, `Renew`,
  and `Release` returns `ErrNoKey`, not `ErrNotClaimed`, for a
  never-admitted key, and `Claim` never creates a record through
  `Store`'s insert-if-absent convention outside `Admit`.
- `takeover_test.go` — `Takeover` fails with `ErrNotStale` while the
  lease is live and succeeds once it expires, bumping the fence;
  fails with `ErrNotClaimed` against a pending or terminal record and
  `ErrNoKey` against a never-admitted key; a `Renew` from the old
  owner's fence after a successful `Takeover` returns `ErrFenced`;
  `TakenOverEvent` fires once, naming the new owner.
- `complete_test.go` — `Complete` marks a record done and blocks every
  direct and transitive dependent, with a deterministic `BlockedBy`
  when two failures could name the same dependent; a two-hop and a
  three-hop cycle each terminate with the originally failed key kept
  at its own terminal status; `Complete` rejects a stale fence, a
  non-`StatusClaimed` record, an already-terminal record (even under
  a matching fence), an out-of-range `status` (checked before any
  `Store` call, even against a never-admitted key), and a
  never-admitted key with `ErrNoKey`; `Blocked` returns `false` for
  both an unblocked and a never-admitted key.
- `snapshot_test.go` — `Snapshot` lists every record; `Encode` then
  `Decode` round-trips every field and rejects malformed JSON or an
  out-of-range `Status`; `Restore` on a fresh `Ledger` reproduces
  every prior `State` result.
- `mem_store_test.go` — `CompareAndSwap` rejects a call whose
  `(Sequence, Status, Fence, Rev)` tuple mismatches, accepts a
  zero-value `old` against an absent key, and bumps `Rev` by one on
  every successful write regardless of which other field changed;
  `Range` visits every record exactly once.
- `admit_integration_test.go` — admit, claim, renew twice, complete
  failed, and assert a dependent's blocked state, through one
  `Ledger` with a real `events.Bus` collecting every event in order.
- The five `*_race_test.go` files race `Claim`, `Admit`, `Takeover`
  against `Claim`, two concurrent `Renew` calls, and two concurrent
  `Complete` calls (one `StatusCompleted`, one `StatusFailed`) against
  the same key, each asserting exactly one winner, the correct
  sentinel for the loser, and the matching event firing exactly once.
  `renew_race_test.go` asserts a wrapped `Store`'s `CompareAndSwap`
  call count exceeds two, proving the `Rev`-driven retry actually
  fires. `complete_race_test.go` also holds
  `TestCompleteFailedBlocksDependentAfterConcurrentClaim`, a
  deterministic regression test: a wrapped `Store` fires a concurrent
  `Claim` on a dependent right after the blocking walk's `Range`
  snapshot returns, and the dependent still ends `StatusBlocked`,
  proving pass two's reload-and-retry closes the gap a single-attempt
  `CompareAndSwap` would leave open.
- `admit_bench_test.go` — `Admit` throughput against `MemStore` under
  increasing key counts, reporting ops/sec and allocs/op with no fixed
  budget, since `MemStore`'s locking varies with `GOMAXPROCS`.
- `task_state_test.go` table-drives every `TaskState.Validate` rule.
  `context_test.go` covers the retry loop's `ctx.Err()` exit, the
  `Store`-level context checks, `Snapshot.Encode`'s and `Restore`'s
  error paths, and `Blocked`'s `Store.Load` error propagation.
  `helpers_test.go` holds the shared fixtures every other file reuses.

gate, the Semgrep scan and probes, and the coverage floor. `ledger`'s

`policy/layers.json` row `"ledger": ["machine", "events"]` predates
