## Phase 5: flow sequential runner — implementation plan

### Design decision (resolved with user)
The plan's "caller-owned ack transport" conflicted with Run's signature, which has no transport parameter, and no transport/callback type exists in the repo. **The user chose Option A: add an ack-callback parameter to `Run`.** This is a deliberate deviation from the phase-plan API signature and is recorded here and in the builder report.

### New API (flow package)
- `type Status string` — the run result status. Named constants replace string literals (AGENTS.md enum rule). Proposed: `StatusDone` for a completed sequential run; a blocked/stopped run returns the last reached status plus an error. Exact constant set is finalized by the planner and pressured by the plan-reviewer.
- `Run(ctx context.Context, d *Definition, m *machine.Definition, in machine.InOut, ack func(envelope.Ack) (envelope.Ack, bool)) (Status, machine.InOut, error)` — walks the step graph in topological/declaration order. The body is inside `package flow`, so it reads the unexported `d.steps` and `d.roots` directly; no new accessor is required.
  - The `ack` callback is the caller-owned transport hook (Option A). The runner builds a pending `envelope.Ack` per step, calls `ack` to resolve it, and treats a returned non-`AckConfirmed` as a blocked gate: the run stops before that step fires (prevents any unconfirmed ack from advancing).
  - Each step fires through `m` by binding the current status and the step's `To` to the unique machine transition row `{From: cur, To: machine.Status(step.To)}`, using that row's trigger. `m.Fire(ctx, cur, trig, in)` returns `(to, out, err)`. A machine Guard rejection (failed gate) surfaces as the Fire error and stops the run. The output `out` feeds the next step's input.
  - No parallel panels, no error join, no chaining — those stay in phases 6 and 7.

### Files changed
1. `flow/runner.go` (or `status.go` + `runner.go`) — `Status` type + constants, and `Run`. One concern per file, functions ≤ 80 lines, files ≤ 500 lines. Every exported symbol gets a doc comment starting with its name.
2. `policy/layers.json` — set the `flow` row to `["envelope", "machine"]` (the deps gate fails without this). flow.md always planned this edge.
3. `docs/plans/flow.md` — update the Status line and API section to reflect the landed sequential runner; keep the five required sections. Record the signature deviation.
4. `docs/architecture.md` + `docs/packages/flow.md` + `flow/doc.go` — update module-map text so docs match the runner (flow now imports machine and envelope). Keep prose in Simplified Technical English (≤ 25 words/sentence), run `check_prose.py`.
5. `api/flow.txt` — regenerate via `make api-update`; commit the lock change in the same change.

### Tests (in `flow/flow_test/`)
- `phase05_tdd_test.go` — red-green cases for `Run`. Assertions written first, confirmed to fail on the empty runner, then implemented. Red steps recorded in comments like the machine tests do.
- `phase05_integration_test.go` — a linear three-step graph using the real `machine.Definition` and the real `envelope.Ack` flow (never a fake). Proves (a) execution order, (b) a failed machine gate stops the run, (c) an unconfirmed ack callback blocks the next step. Cross-package coverage: a real value crosses into machine and envelope per the test-review skill.
- `phase05_perf_test.go` — benchmark `Run` on the three-step linear graph. Target under 1 ms. State the allocation budget and assert it, mirroring the machine alloc-budget tests. Document the measured baseline in comments.

### Delivery loop
Driven by the `delivery` skill using this repo's subagents, in order, never skipping a stage and never letting an agent grade its own work: planner → plan-reviewer (hostile, before code) → builder → reviewer (adversarial, after code) → final `make verify` + commit (`type(scope): imperative subject`). Escalate to the user after 3 failed rounds at any stage or if a gate failure looks like a gate bug.
